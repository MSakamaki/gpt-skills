# 更新履歴

## 1.4.0 — 2026年9月19日

確認していないことを「なし」と書かないようにし、`SKILL.md` の一部を条件付き読み込みへ移しました。

### 変更

- **未回答を「なし」と書きません** (I-18)。1.3.0 で確認ターンを入れた後も推論が残っていました。原因はスキーマ自身が未回答を「なし」「指定なし」「unknown」と書くよう指示していたことです。値の状態を確定・委任・未回答の 3 つに分け、未回答は `<未回答>` と書きます
- **未回答はそのまま下流へ渡します。** 下流は「制約が無い」と読み替えません。その値が必要になった工程が、そのときに確認します。依頼の整理でトーンを聞く必要はなく、画面文章を書く工程が必要とした時点で聞きます
- ユーザーが「指定はありません」と答えたときだけ「なし」と書けます。この場合は確定した答えです
- 機能や資料の制約で取得できていない事実は `<未取得>` と書きます (テンプレートの検査結果、プレビュー画像)
- 未回答を既定値で埋めていた `brief-normalizer`、`audience-analyzer`、`delivery-artifact-planner` のスキーマを書き換えました
- **`references/TURN-FORMATS.md` を追加**し、条件付きでしか要らない記述を `SKILL.md` から移しました。確認ターンの選択肢の作り方、`FAIL` と `BLOCKED` の書き方、差し戻し先の対応表、`review_result` の形式です。`SKILL.md` は 33.6KB から 30.2KB になりました
- 確認ケース Q15〜Q18 と静的検査 S14 を追加しました

## 1.3.0 — 2026年9月19日

工程の中で分からないことを、推論で埋めずに確認するようにしました。

### 変更

- **推論で埋めません** (I-17)。上流の成果物に書かれておらず、埋め方で成果物が実質的に変わる点は、選択式でユーザーに確認してから埋めます。すでに書かれている事項、高い確度で読み取れる事項、どう埋めても結果が変わらない事項は聞きません
- **ターンに 2 つの形ができました** (I-16)。工程の実行中に確認が要るときは**確認ターン**で論点を 1 つ聞きます。工程が終わったときだけ**完了ターン**で結果と成果物を出します
- **確認ターンでは YAML を出しません。** 工程がまだ終わっておらず、記録すべき結果が無いためです。状況の表示は、次の工程へ進むかを判断する完了ターンだけで行います
- **Reviewer と Validator は確認しません。** 判定する立場なので、判定の内容をユーザーへ聞くことは検証の委譲にあたります。判定に必要な事実が無ければ BLOCKED にします
- **価値判断には推奨を付けません。** 目的、優先順位、主張の強さ、進行の好みなど本人が決めるべき論点では、選択肢の違いを中立に説明します。委任の選択肢も置きません
- 「残りは任せる」と明示されたら埋めて進めますが、埋めた内容と根拠を記録します。価値判断にあたる論点だけは、まとめての委任でも改めて確認します
- 確認で得た回答を、結果ブロックの `clarifications` に聞いた内容と対で残します
- 曖昧さが集まりやすい工程 (依頼の構造化、聴衆分析、利用形態、主張、証拠の選定、組み上げのレイアウト選び) に、確認しうる論点を書きました
- `SAMPLES.md` に確認ターンの節を追加し、通しの進行にも確認の例を入れました
- 確認ケース Q01〜Q14 と静的検査 S13 を追加しました

## 1.2.0 — 2026年9月19日

ターン末の案内を選択式にし、入力の負担を下げました。

### 変更

- **「次にすること」を選択式にしました。** 選択肢に `A` から始まるアルファベットの記号を付け、記号 1 文字で答えられるようにしています。数字を使わないのは Slide 番号と紛れるためです。推奨は常に `A` に置きます
- **選択肢ごとに 4 観点を書きます。** 何をする工程か、選ぶと何が変わるか、いつこれを選ぶか、取り消せるか、の 4 つです。行数では規定していません。初めて出る工程は厚く、2 回目以降は薄く書きます。`状況` のような毎回出る操作は 1〜2 行です
- **`9` で深掘りできます。** 何も実行せず、各選択肢を詳しく説明して同じ選択肢を再提示します
- **`0` は使いません。** 他のスキルの「AI に任せる」に当たる入力ですが、このスキルで AI が選べるのは既定の次工程だけで `A` と同じになるためです。打たれた場合は実行せず、推奨が `A` であることを伝えます
- **実行前に、何を選んだと解釈したかを 1 行返します。** 記号は短いぶん取り違えが起きやすく、「A案・B案」を比較するデッキでは `B` が案の名前と紛れるためです
- `SAMPLES.md` の全例を選択式へ書き換え、記号の答え方 (`9`、`0`、紛らわしい記号) の節を追加しました
- 確認ケース N01〜N07 を更新し、N08〜N15 と静的検査 S12 を追加しました

### guided-clarification との関係

記号・`0` の有無・記号の意味の持続・説明の深さがすべて異なるため、**継承ではなく参照**として整理しました。共通するのは、1 ターンに 1 つ選ばせる、数合わせで弱い選択肢を作らない、推奨を 1 つだけ付ける、自由入力を常に有効とする、深掘りの記号を持つ、の 5 点だけです。この変更を `slide-visual` へ持ち込むことはしません。

## 1.1.0 — 2026年9月19日

初版の実地検証で見つかった 3 点を是正しました。

### 変更

- **作業言語と成果物の声を分離** (I-15)。依頼の「対象者は幼稚園児、ひらがなで」といったトーン・表記の指定が、`audience_profile` などの作業の記録まで変えてしまう問題を是正しました。指定は `presentation_brief.deliverable_voice` に記録し、聴衆が読む・聞く文字列にだけ適用します。Context の出力スキーマでは該当項目に `[成果物の声]` と印を付けています。作業の記録・所見・案内は常に日本語の常体で書きます
- **各ターンを「次にすること」で終える** (I-16)。工程が切り替わった後に現在の状況しか出ず、利用者が次に何をすればよいか分からずに作業が止まる問題を是正しました。そのまま打てる操作と、それを選ぶと何が起きるかを 1 行ずつ示します。`BLOCKED` では足りないものと渡し方を、`FAIL` では所見の要点を日本語で書きます
- **`SAMPLES.md` を追加**。起動から完成状態までのターンの並びを実物の形で示します。FAIL と差し戻し、BLOCKED、状況確認、人間承認、言語の分離、内容モデルによる分岐を個別の例で載せています。実行時には読み込みません
- `audience_profile` に `voice_consistency` を追加。読解水準と専門性が矛盾する場合を記録します
- 確認ケースに L01〜L07 (言語とトーン) と N01〜N07 (ターン末の案内)、静的検査 S09〜S11 を追加しました

### 維持した条件

Context の構成と責務、1 Turn = 1 Context、生成と検証の分離、差し戻し原則、PPTX 既定とテンプレート必須、画像を生成しない方針、ドメインガイドの本文は変えていません。

## 1.0.0 — 2026年9月19日

初版。

### 構成

- 1 スキル・Context Router 構成。Control / Foundation / Deck Design / Slide Content / Visual Design / Rendering-Build / Delivery / Validation の 8 段階、69 Context (Designer 32・Reviewer 32・Validator 4・Navigator 1)
- `references/REGISTRY.md` に全 Context の入出力・遷移・差し戻し先を集約。Context ファイルは `references/contexts/` 配下に段階ごとのディレクトリで 1 本ずつ
- ドメイン知識の正本として `references/domain-guide.md` を同梱。元原稿の引用マーカーを出典表記へ置換し、見出しに番号を付し、出典対応表を付録として追加。本文は変更していない

### 決めたこと

- 1 Turn = 1 Specialist Context。人間の操作なしに次 Context へ進まない。FAIL は差し戻し先を示して止まり、自動修復しない
- Artifact は会話中の YAML ブロックを正本とし、Reviewer の PASS を承認とする。人間が Reviewer を経ずに承認する場合は記録に残す。Validator は人間承認で代替できない
- 出力は PPTX を既定とし、文字・表・Chart・図形はテンプレート上のネイティブ要素で組み上げる。PPTX テンプレートは必須 (無ければ `delivery-artifact-planner` が BLOCKED)
- 画像は生成しない。`image-generator` は受け渡し仕様と配置枠を作り、ユーザーが別途作った画像をはめ込む
- コード実行機能が無い環境では Build 系 Context を BLOCKED とし、テキストの仕様を生成物と称しない
- `presentation-preflight-reviewer` と `outcome-evaluator` は実測情報・測定データが無ければ BLOCKED。推測で PASS にしない

### 検証の区別

配布時の検査は静的検査 (構造・YAML・内部参照・Registry の整合) です。ZIP の検査・作成は、アカウントへの反映や、実際の起動・会話動作・生成物の品質の検証を意味しません。
