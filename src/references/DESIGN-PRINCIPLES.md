# Design Principles

Review Round へ直接割り当てず、Skill 全体の挙動へ反映する原則。Router はこれらを Method 候補として選択しない。

Design Principle へ分類する基準は 2 つある。

1. 単独の攻撃手順ではなく、検証全体の進め方を規定するもの
2. 独立した複数の参加者を本質的に必要とし、単一モデルの役割分離では原型を再現できないもの (plans2 §28)

各原則には、その原則を満たしているかを実行後に確認できる形で `Check` を置く。

---

## MARE_PROCESS_SEPARATION

### 原則

要件・候補・主張を **生成する役割** と、それを **検証する役割** を同じ担当に兼ねさせない。

### 反映

- 主回答者が生成した要件・原因・対策を、同じ turn で主回答者自身が妥当と判定しない。判定は Reviewer と Critic の工程で行う。
- Method の出力 (候補要件、失敗原因、仮説、defeater) は生成された時点では候補であり、採否判定を経て初めて回答へ反映される。
- 生成の網羅性と、判定の厳密さを同じ基準で評価しない。

### Check

回答へ反映された指摘のうち、生成と採否判定が同一工程で完結したものが無いこと。

### Evidence

`PAPER-MARE` (arXiv:2405.03256v1)。MARE は RE プロセスを elicitation / modeling / verification / specification の 4 タスクへ分け、5 エージェント・9 アクションで分担し、中間成果物を共有 workspace 経由で受け渡す。要件モデルの生成において既存手法を上回ったと報告している。

本 Skill は MARE を再現しない。工程分離という設計上の含意だけを採る。

### なぜ Round へ割り当てないか

MARE は検証の攻撃手順ではなく、プロセス全体の分業構造だから。

## REQUIREMENTS_MAD

### 原則

要件に関する判断を、単一の視点で確定させない。対立する立場を明示的に置いてから収束させる。

### 反映

- REQUIREMENTS_ELICITATION を実行する Round では、候補要件に対して「不要とする立場」も構成してから採否を決める。
- 多数の候補が挙がったことを品質の指標にしない。

### Check

採用した候補要件について、不要とする立場を検討した記録があること。

### Evidence

`PAPER-MAD-RE` (arXiv:2507.05981v1)。RE へ Multi-Agent Debate を適用し、RE classification において実現可能性を評価している。あらゆる要件整理タスクへの有効性を示した研究としては扱わない。

### なぜ Round へ割り当てないか

評価範囲が RE classification に限られ、独立した Round を占めるだけの裏付けがないため。

## ADVERSARIAL_COLLABORATION

### 原則

対立する立場を扱うとき、**何が観測されたら自分の立場を弱めるか** を各立場に先に定義させる。

### 反映

- Problem Profile に `CONFLICT` が含まれる場合、回答案が扱う各立場について、その立場が退く条件を先に書き出してから比較する。
- 退く条件を定義できない立場は、その旨を明示する。定義できないこと自体が検証サマリーに載る情報になる。
- 立場の比較を「どちらが正しいか」ではなく「何が分かれば決着するか」へ変換する。

### Check

`CONFLICT` を含む依頼で、各立場の反証条件が記録されていること。

### Evidence

`PAPER-ADV-COLLAB` (DOI: 10.1037/amp0001391)。再配布条件を満たさないため PDF は同梱していない。

### なぜ Round へ割り当てないか

原型は独立した研究者同士が事前に合意して共同研究を行う枠組みであり、単一モデルが双方を演じても再現にならないため (plans2 §16, §28)。**単一モデルが双方の立場を書いた場合、独立した参加者による Adversarial Collaboration を実施したとは記録しない。**

## FORECAST_CALIBRATION

### 原則

将来に関する主張は、可能な範囲で検証可能な形へ変換する。

### 反映

- 「可能性が高い」「ほとんど起きない」のような表現が判断に効いている場合、確率、範囲、または「いつまでに何が観測されれば当たりと言えるか」を添える。
- 数値化できない場合は、数値化できない理由を書く。根拠のない数値を置かない。
- 断定を弱めるだけの書き換えを行わない。検証可能性が上がらない書き換えは改善ではない。

### Check

`FORECAST` または `UNCERTAINTY` を含む依頼で、判断に効く将来主張に検証条件が付いていること。

### Evidence

`PAPER-FORECAST` (DOI: 10.1177/0963721414534257)。予測を明示的な確率として比較可能にし、精度を追跡する枠組みを扱う。再配布条件を満たさないため PDF は同梱していない。

### なぜ Round へ割り当てないか

攻撃手順ではなく、出力表現に関する規律だから。

---

## INDEPENDENT_FIRST

### 原則

検証者に、他者の判断を見る前に自分の判断を出させる。

### 反映

- Reviewer は、前 Round の指摘や Critic の判定を参照する前に、その Round の Method に従って自分の指摘を作る。
- Critic は、Reviewer の指摘を読む前に、固定された回答案を独立に一読する。
- 各担当へ、前の担当の非公開の思考過程を渡さない。渡すのは確定した回答仕様、固定した回答案、根拠、その Round の観点に限る。

### Check

各 Round の Critic が、Reviewer の指摘とは独立に回答案を確認した記録があること。

### Evidence

`PAPER-AR` (arXiv:2608.18167v1)。原論文は、2 つの LLM Agent に合意を求めると互いに同調し、Critic が Reviewer の主張へ譲って本物の欠陥が落ちる false consensus が起きることを報告している。独立性の確保はこの failure mode への対処として本 Skill が採る規律である。

### なぜ Round へ割り当てないか

すべての Round に常時かかる制約だから。

---

## MINORITY_DISSENT

### 原則

少数意見を、合意へ収束させるために削らない。

### 反映

- Critic の `DISAGREE CONCERN` を、根拠が示せないという理由だけで一律に破棄しない。Reviewer が確認できる根拠を示せない場合は、指摘を削除するのではなく範囲を狭める。
- 安定化後も残った対立は、合意に見せかけず対立として記録する。
- 採用しなかった指摘のうち、信頼性の判断に役立つものは検証サマリーへ残す。
- Consensus に達したことを成功条件にしない。

### Check

安定化の過程で削除した指摘について、削除の根拠が記録されていること。

### Evidence

`PAPER-AR` (arXiv:2608.18167v1)。原論文は Critic の判定を AGREE / DISAGREE EVIDENCE / DISAGREE CONCERN の 3 区分へ分け、DISAGREE CONCERN に対しては Reviewer 側へ根拠提示を求める応答規則を置いている。

### なぜ Round へ割り当てないか

すべての Round の安定化工程にかかる制約だから。
