# 敵対的検証回答

## 基本契約

以下の手順を順番どおりに実行する。入力確認と質問の段階が完了するまで、依頼への回答案、敵対的検証、結論を作成または提示しない。

ユーザー自身が明示した言葉だけを入力済みとして扱う。推論、過去の記憶、暗黙の文脈から必須項目を補完しない。`なし`は有効な明示入力として扱う。すでに入力された値は保持し、ユーザーが変更した場合または重大な矛盾が生じた場合を除き、再質問しない。

次の10項目の状態を保持し、ユーザーから回答を受けるたびに更新する。

1. 目的
2. 依頼内容
3. 背景・前提
4. 対象者
5. 入力情報
6. 制約条件
7. 成功条件・評価基準
8. 出力形式
9. 詳しさ・トーン
10. 根拠・検証方法

## 1. 必須入力をすべて集める

スキルを起動した依頼と、その後の返信から、ユーザーが10項目のうち何を明示したかを判定する。

未入力の項目がある場合は、次のように対応する。

- 未入力項目だけを一覧化する。
- 1回の返信で回答できるよう、まとめて尋ねる。
- 次の簡潔でコピー可能な入力欄から、入力済みの行を取り除いて提示する。

```markdown
1. 目的：
2. 依頼内容：
3. 背景・前提：
4. 対象者：
5. 入力情報：
6. 制約条件：
7. 成功条件・評価基準：
8. 出力形式：
9. 詳しさ・トーン：
10. 根拠・検証方法：
```

- 質問を提示した時点でそのターンを終了する。元の依頼への回答を始めない。

すべての項目に明示的な値が入るまで繰り返す。未回答項目を自動的に`なし`として扱わない。

## 2. 確認質問を反復する

10項目がすべて揃ったら、統合した依頼について、回答を大きく変え得る不確実性を確認する。次の順で点検する。

- 曖昧さまたは未定義語
- 項目間または出典間の矛盾
- 対象範囲と除外範囲
- 優先順位と相反関係
- 例外と失敗条件
- 期限または基準時点
- 測定可能な判断基準
- 指定された検証水準を満たすために不足している根拠

重大な不確実性が残る場合は、次のように対応する。

1. 更新した10項目を簡潔に提示する。
2. 必要な質問を重要度順に並べ、可能な限り1回の返信で回答できるようまとめる。
3. 各質問に、その回答が結果へ与える影響を短い理由として添える。
4. 質問を提示した時点でそのターンを終了し、ユーザーの回答を待つ。
5. 影響を受ける項目を更新し、この点検項目の先頭から再評価する。

回答が結果を大きく変え得る場合だけ追加質問する。見た目上の好みや、低リスクで最終回答に明示できる仮定を理由に、質問を長引かせない。

重大な質問が残っていない場合は、`質問なし`と明示して同じターン内で次へ進む。

## 3. 合意した依頼条件を確定する

10項目と、合意済みの仮定・優先順位を簡潔に提示する。これを回答仕様として扱う。

確定時に重大な矛盾が見つかった場合は、確認質問へ戻る。それ以外では、調査や検証中に回答仕様を暗黙に変更しない。避けられず追加した仮定は記録し、最終回答で明示する。

## 4. 検証戦略を選択する

回答案を作る前に、この依頼で回答が失敗しそうな理由を特定し、それに適した検証方法を選ぶ。

読み込みは必要な範囲だけに限る。`references/METHOD-ROUTING.md`を読み、そこで選んだMethodのCardだけを読む。`references/papers/`配下のPDFをすべて読まない。PDFは根拠の確認とMethod Card自体の監査にだけ使い、実行仕様はMethod Cardを正本とする。

1. **問題プロファイルを作る** — 確定した回答仕様を`REQ` `DECISION` `CAUSE` `PLAN` `UNCERTAINTY` `CONFLICT` `ASSURANCE` `FORECAST` `FACT` `GENERIC`へ分類する。Primaryを0〜1個、Secondaryを0個以上持つ。分類できない依頼を無理に既存カテゴリへ入れない。
2. **Failure Modeを抽出する** — 問題プロファイルとは独立に、回答を誤らせうる要因を`F01`〜`F16`から検出し、`CRITICAL` `MAJOR` `MINOR`で重み付けする。
3. **`references/METHOD-ROUTING.md`を読む。**
4. **Method候補を出す** — Failure Modeから候補を引く。問題プロファイルからMethodを直接決めない。
5. **適用条件を評価する** — 候補のMethod Cardの`Applicable When`と`Do Not Use When`で絞る。適用条件を確認できない候補は落とす。
6. **最大3 Methodを選ぶ** — `CRITICAL`から順にCoverageする。3つ使うことを目標にしない。数値スコアは使わない。適用可能な専門Methodがなければ`CORE-AR`だけで進む。
7. **Route Checkを実施する** — `RC1`〜`RC8`を確認する。問題があればRouteを1回だけ選び直す。無限に再評価しない。
8. **選んだMethod Cardだけを読む。**
9. **必要な場合だけ対応PDFを確認する** — Method Cardの記述に疑義がある場合に限る。同梱されていないPDFをウェブから取得しない。
10. **3回のReview RoundへMethodを割り当てる** — Round 1にPrimary、以降を順に割り当てる。Methodが3つに満たないRoundは`CORE-AR`の一般攻撃とする。

問題プロファイルに`CONFLICT` `FORECAST` `UNCERTAINTY`が含まれる場合、または要件・原因・対策を生成した役割にそのまま検証させそうな場合は、`references/DESIGN-PRINCIPLES.md`も読み、該当する原則を検証工程へ反映する。これらの原則はReview Roundとして割り当てない。

### 共通プロトコル CORE-AR

すべてのRoundは`references/methods/METHOD-CORE-AR.md`の枠組みに従う。採用するのは次の構造だけであり、この構造があらゆる種類の回答で精度を高めることが実証されたとは扱わない。根拠となる研究はコードレビューを対象としており、一般回答への適用は限界のある転用である。

- 主回答者、レビュー担当、批判担当を分離する。
- レビュー中は回答案を固定する。
- 批判担当はレビュー担当の指摘自体も検証する。
- 不同意には具体的な根拠を要求する。
- 合意すること自体を正しさより優先しない。
- レビューが安定してから回答を修正する。

### 実行モード

複数の独立したサブエージェントを利用できる場合は`independent_agents`、利用できない場合は`role_separated_single_model`として続行する。単一モデルの場合も処理を止めず、許可も求めない。ただしそれを独立した複数エージェントによる検証とは記録しない。独立した複数の参加者を本質的に必要とする方法は、Review Roundへ割り当てず`references/DESIGN-PRINCIPLES.md`の原則として扱う。

### 選択結果を記録する

問題プロファイル、Failure Modeと重み、選んだMethodとそれぞれがCoverするFailure Mode、外した主要候補と理由、Route Checkの結果、Coverageできなかった Failure Mode、実行モードを保持する。

## 5. 調査して暫定回答を作る

項目10に従って調査し、最新性が重要な場合は現在の一次資料を使う。ウェブ検索は、項目10がそれを求める場合と、回答内容として最新の一次資料が必要な場合に限って使う。検証方法論をウェブから探し直さない。重要な事実主張について、主張と出典の簡潔な対応表を保持する。出典が競合する場合は差異を示し、どの出典を採用するか理由を説明する。出典を捏造しない。重大な情報不足は未確認と明示する。

確定した回答仕様に従って暫定回答を作る。内部的に版を`V0`とする。この段階では最終回答として提示しない。

## 6. 敵対的検証を必ず3回行う

前の検証で問題が見つからなかった場合も、3回すべて実行する。このユーザー指定の固定回数は、`CORE-AR`の根拠となる研究が持つ初回通過時の終了規則より優先する。

サブエージェントを利用できる場合は、各回で新しいレビュー担当と批判担当を使用する。確定した回答仕様、固定した回答案、関連する根拠、その回に割り当てたMethodとそのMethod Cardを渡すが、以前の担当者の非公開の思考過程は渡さない。別の担当を利用できない場合も処理を止めず、許可も求めず、同一モデル内で役割を分けて続行する。その場合は完全な独立性や論文に忠実な複数エージェント実行を装わず、役割分離による検証であることだけを記録する。

レビュー担当は、前の回の指摘や批判担当の判定を参照する前に、その回のMethodに従って自分の指摘を作る。批判担当は、レビュー担当の指摘を読む前に、固定した回答案を独立に一読する。

各検証回`i = 1..3`で、次を実行する。

1. **固定** — `V(i-1)`を固定する。レビュー担当と批判担当は確認できるが、内側の検証中に編集しない。
2. **攻撃** — レビュー担当`Rᵢ`は、その回に割り当てたMethod Cardの`Procedure`に従って攻撃し、`Output`の形式で指摘を出す。Methodを割り当てていない回では、`CORE-AR`の一般攻撃として、具体的な誤り、反例、見落とし、隠れた前提、因果の飛躍、弱い根拠、制約違反、対象者との不一致を探す。各指摘には、回答案中の該当箇所、出典、または回答仕様の項目を根拠として添える。Method Cardの`False Positive Guard`に該当する指摘は出さない。
3. **レビューへの批判** — 新しい批判担当`Cᵢ`は、固定した回答案を独立に確認し、各指摘とレビュー全体の網羅性を監査する。あわせて、その回のMethodが今回の依頼に本当に適用可能か、`Applicable When`と`Do Not Use When`に照らして確認する。レビューが空、無条件承認、または弱い場合は、重大な問題を見落としていないか積極的に検証する。各指摘を次のいずれかで判定する。
   - `同意`：指摘をそのまま採用する。
   - `証拠による不同意`：指摘と矛盾する具体的な出典または回答案中の根拠を示す。
   - `懸念による不同意`：直接反証する証拠がない場合に、認識上または方法上の具体的な異議を示す。
4. **安定化** — 不同意をレビュー担当`Rᵢ`へ返す。`証拠による不同意`では、示された根拠に従って指摘を修正または削除する。`懸念による不同意`では、具体的な裏付けを示せる場合だけ指摘を維持し、それ以外は範囲を狭めるか削除する。レビュー文だけをやり取りし、最大5回の内側反復で内容を安定させる。
5. **判定** — 安定した各指摘の妥当性と影響度を評価する。`採用`または`不採用`、簡潔な理由、使用した根拠を記録する。網羅的に見せる目的で推測的な指摘を採用しない。
6. **修正** — 主回答者が採用した指摘を反映して`Vᵢ`を作り、簡潔な変更記録を残す。
7. **Invariant Gate** — `Vᵢ`について次をすべて確認する。専門Methodがこの確認を置き換えることはない。
   - `G1 SPEC`：確定した回答仕様を満たすか
   - `G2 LOGIC`：内部に矛盾がないか
   - `G3 FACT`：事実の記述と根拠が一致するか
   - `G4 UNCERTAINTY`：推測を事実として書いていないか
   - `G5 CONSTRAINT`：制約条件、安全上の要請、上位のルールに違反していないか
   - `G6 SOURCE`：引用が、それが支えるとされる主張を実際に裏付けるか
   - `G7 OVERCORRECTION`：修正によって、正しかった記述を弱めたり情報を失ったりしていないか

各回は、割り当てたMethodによる攻撃と`Invariant Gate`の両方で構成する。Methodを割り当てていない回では、次の観点のうちその回までに使っていないものを選ぶ。

- 論理的な妥当性、完全性、確定した回答仕様への適合
- 事実の正確性、出典の質、最新性、競合する証拠、反例
- 対象者への適合、実行可能性、境界事例、失敗条件、使いやすさ

同じ批判の言い換えで3回を済ませない。重大な問題を見つけた場合は、その回の重点外でも検証対象に含める。

非公開の思考過程は開示しない。監査可能な情報として、指摘、参照した根拠、判定、採否、反映した修正、残存リスクだけを保持する。

## 7. 最終回答を提示する

ユーザーが指定した出力形式、詳しさ、トーンに従う。項目8または9が`なし`の場合は、読みやすく簡潔かつ十分なマークダウンを使う。

確定した回答仕様で別の順序が指定されていない限り、次の順で出力する。

1. 最終回答
2. 重要な前提・不確実性
3. 根拠・出典
4. 検証サマリー

検証サマリーには、問題プロファイル、検出した主なFailure Mode、選んだMethodとその理由、各検証回の主要な攻撃観点、採用した修正、残存リスクを、それぞれ簡潔な行または箇条書きで示す。Coverageできなかった Failure Modeと、使用したMethod Cardが記載する転用上の限界があれば併記する。実行モードが`role_separated_single_model`の場合は、独立した複数エージェントによる検証ではないことを明示する。信頼性の判断に役立つ場合だけ、重要な不採用指摘も示す。非公開の思考過程や内部検討の逐語記録は開示しない。

次を明確に区別する。

- 確認済みの事実
- 推論
- 合意済みまたは避けられない仮定
- 未解決の不確実性

送信前に、確定した要件をすべて満たしたこと、3回の検証を完了したこと、引用が直前の主張を裏付けること、未確認事項を確認済みの事実として示していないことを確認する。出典URLを引用した場合は、最後の修正後にそれらをすべて開き、意図した出典と該当箇所に到達することを確認する。壊れたリンク、形式が不正なリンク、内容が一致しないリンクは修正または削除する。
