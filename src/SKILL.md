# 敵対的検証回答

## 基本契約

以下の手順を順番どおりに実行する。入力確認と質問の段階が完了するまで、依頼への回答案、敵対的検証、結論を作成または提示しない。

ユーザー自身が明示した言葉だけを入力済みとして扱う。推論、過去の記憶、暗黙の文脈から必須項目を補完しない。`なし`は有効な明示入力として扱う。すでに入力された値は保持し、ユーザーが変更した場合または重大な矛盾が生じた場合を除き、再質問しない。

次の10項目の状態を保持し、ユーザーから回答を受けるたびに更新する。

1. 目的
2. 依頼内容
3. 背景・前提
4. 対象者
5. 入力情報
6. 制約条件
7. 成功条件・評価基準
8. 出力形式
9. 詳しさ・トーン
10. 根拠・検証方法

## 1. 必須入力をすべて集める

スキルを起動した依頼と、その後の返信から、ユーザーが10項目のうち何を明示したかを判定する。

未入力の項目がある場合は、次のように対応する。

- 未入力項目だけを一覧化する。
- 1回の返信で回答できるよう、まとめて尋ねる。
- 次の簡潔でコピー可能な入力欄から、入力済みの行を取り除いて提示する。

```markdown
1. 目的：
2. 依頼内容：
3. 背景・前提：
4. 対象者：
5. 入力情報：
6. 制約条件：
7. 成功条件・評価基準：
8. 出力形式：
9. 詳しさ・トーン：
10. 根拠・検証方法：
```

- 質問を提示した時点でそのターンを終了する。元の依頼への回答を始めない。

すべての項目に明示的な値が入るまで繰り返す。未回答項目を自動的に`なし`として扱わない。

## 2. 確認質問を反復する

10項目がすべて揃ったら、統合した依頼について、回答を大きく変え得る不確実性を確認する。次の順で点検する。

- 曖昧さまたは未定義語
- 項目間または出典間の矛盾
- 対象範囲と除外範囲
- 優先順位と相反関係
- 例外と失敗条件
- 期限または基準時点
- 測定可能な判断基準
- 指定された検証水準を満たすために不足している根拠

重大な不確実性が残る場合は、次のように対応する。

1. 更新した10項目を簡潔に提示する。
2. 必要な質問を重要度順に並べ、可能な限り1回の返信で回答できるようまとめる。
3. 各質問に、その回答が結果へ与える影響を短い理由として添える。
4. 質問を提示した時点でそのターンを終了し、ユーザーの回答を待つ。
5. 影響を受ける項目を更新し、この点検項目の先頭から再評価する。

回答が結果を大きく変え得る場合だけ追加質問する。見た目上の好みや、低リスクで最終回答に明示できる仮定を理由に、質問を長引かせない。

重大な質問が残っていない場合は、`質問なし`と明示して同じターン内で次へ進む。

## 3. 合意した依頼条件を確定する

10項目と、合意済みの仮定・優先順位を簡潔に提示する。これを回答仕様として扱う。

確定時に重大な矛盾が見つかった場合は、確認質問へ戻る。それ以外では、調査や検証中に回答仕様を暗黙に変更しない。避けられず追加した仮定は記録し、最終回答で明示する。

## 4. 指定論文を確認する

回答案または敵対的検証を始める前に、ウェブ検索とPDFの論文(`references\2608.18167v1.pdf`)を使って概要を確認する。

論文のタイトル、著者、版、日付、現在の公開状態、本文の閲覧可否、実際の敵対的レビュー手順を確認する。論文に記載された主張、一般知識、コードレビュー手順を一般的な回答へ応用した本スキル独自の部分を区別する。

論文と手法を検証できた場合だけ先へ進む。URLまたは識別子が無効、論文または手順へアクセス不能、本文から手法を確認不能のいずれかに該当する場合は、次のように対応する。

1. 検証できない具体的な理由を説明する。
2. 正しいURL、PDF、貼り付けた本文、または名称を示した代替手法を使用する明示的な許可を求める。
3. 処理を停止する。論文に従ったと主張せず、許可なく別の手法へ置き換えない。

論文を確認できた場合は、検証工程で次の性質を維持する。

- 主回答者、レビュー担当、批判担当を分離する。
- レビュー担当と批判担当がレビュー文を検討している間は回答案を固定し、レビューが安定してから修正する。
- 不同意を明示し、具体的な根拠を必須とする。
- 合意すること自体を正しさより優先しない。

この論文が、あらゆる種類の回答で本応用の有効性を証明したかのように扱わない。一般回答への転用は、限界のある方法論上の応用として扱う。

## 5. 調査して暫定回答を作る

項目10に従って調査し、最新性が重要な場合は現在の一次資料を使う。重要な事実主張について、主張と出典の簡潔な対応表を保持する。出典が競合する場合は差異を示し、どの出典を採用するか理由を説明する。出典を捏造しない。重大な情報不足は未確認と明示する。

確定した回答仕様に従って暫定回答を作る。内部的に版を`V0`とする。この段階では最終回答として提示しない。

## 6. 敵対的検証を必ず3回行う

前の検証で問題が見つからなかった場合も、3回すべて実行する。このユーザー指定の固定回数は、論文にある初回通過時の終了規則より優先する。

サブエージェントを利用できる場合は、各回で新しいレビュー担当と批判担当を使用する。確定した回答仕様、固定した回答案、関連する根拠、その回の検証観点を渡すが、以前の担当者の非公開の思考過程は渡さない。別の担当を利用できない場合は、完全な独立性や論文に忠実な複数エージェント実行を装わない。役割を分けた検証で代替してよいかをユーザーへ尋ね、許可を得てから進む。

各検証回`i = 1..3`で、次を実行する。

1. **固定** — `V(i-1)`を固定する。レビュー担当と批判担当は確認できるが、内側の検証中に編集しない。
2. **攻撃** — レビュー担当`Rᵢ`は、その回の重点に沿って、具体的な誤り、反例、見落とし、隠れた前提、因果の飛躍、弱い根拠、制約違反、対象者との不一致を探す。
3. **レビューへの批判** — 新しい批判担当`Cᵢ`は、固定した回答案を独立に確認し、各指摘とレビュー全体の網羅性を監査する。レビューが空、無条件承認、または弱い場合は、重大な問題を見落としていないか積極的に検証する。各指摘を次のいずれかで判定する。
   - `同意`：指摘をそのまま採用する。
   - `証拠による不同意`：指摘と矛盾する具体的な出典または回答案中の根拠を示す。
   - `懸念による不同意`：直接反証する証拠がない場合に、認識上または方法上の具体的な異議を示す。
4. **安定化** — 不同意をレビュー担当`Rᵢ`へ返す。`証拠による不同意`では、示された根拠に従って指摘を修正または削除する。`懸念による不同意`では、具体的な裏付けを示せる場合だけ指摘を維持し、それ以外は範囲を狭めるか削除する。レビュー文だけをやり取りし、最大5回の内側反復で内容を安定させる。
5. **判定** — 安定した各指摘の妥当性と影響度を評価する。`採用`または`不採用`、簡潔な理由、使用した根拠を記録する。網羅的に見せる目的で推測的な指摘を採用しない。
6. **修正** — 主回答者が採用した指摘を反映して`Vᵢ`を作り、簡潔な変更記録を残す。
7. **再確認** — `Vᵢ`に、修正による新たな矛盾、情報損失、根拠のない断定、形式の逸脱、制約違反がないか確認する。

各回では、異なる観点を優先する。

- 第1回：論理的な妥当性、完全性、確定した回答仕様への適合
- 第2回：事実の正確性、出典の質、最新性、競合する証拠、反例
- 第3回：対象者への適合、実行可能性、境界事例、失敗条件、使いやすさ

同じ批判の言い換えで3回を済ませない。重大な問題を見つけた場合は、その回の重点外でも検証対象に含める。

非公開の思考過程は開示しない。監査可能な情報として、指摘、参照した根拠、判定、採否、反映した修正、残存リスクだけを保持する。

## 7. 最終回答を提示する

ユーザーが指定した出力形式、詳しさ、トーンに従う。項目8または9が`なし`の場合は、読みやすく簡潔かつ十分なマークダウンを使う。

確定した回答仕様で別の順序が指定されていない限り、次の順で出力する。

1. 最終回答
2. 重要な前提・不確実性
3. 根拠・出典
4. 検証サマリー

検証サマリーには、各検証回の主要な攻撃観点、採用した修正、残存リスクを、それぞれ簡潔な行または箇条書きで示す。信頼性の判断に役立つ場合だけ、重要な不採用指摘も示す。非公開の思考過程や内部検討の逐語記録は開示しない。

次を明確に区別する。

- 確認済みの事実
- 推論
- 合意済みまたは避けられない仮定
- 未解決の不確実性

送信前に、確定した要件をすべて満たしたこと、3回の検証を完了したこと、引用が直前の主張を裏付けること、未確認事項を確認済みの事実として示していないことを確認する。最後の修正後に最終回答の引用URLをすべて開き、意図した出典と該当箇所に到達することを確認する。壊れたリンク、形式が不正なリンク、内容が一致しないリンクは修正または削除する。
