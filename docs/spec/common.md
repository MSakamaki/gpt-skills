# Skill 共通仕様

`src/` 配下の全 Skill に共通してかかる規定。**各 Skill の spec (`docs/spec/<skill-name>.md`) は本書を継承し、Skill 固有の事項だけを書く。** 本書と個別 spec が矛盾した場合は個別 spec を優先する (Skill 固有の事情があるということなので、その理由を個別 spec へ書く)。

リポジトリの運用手順 (ビルド・検証・秘密情報スキャン・コミット) は [CLAUDE.md](../../CLAUDE.md) が正本。本書は Skill の**振る舞いと保守**に関する規定だけを持つ。

---

## 1. 正本と責務分離

### 1.1 spec が正本

**spec と実装 (`SKILL.md` ほか) が矛盾する場合、spec を優先する。** 実装だけを変えて spec と食い違わせてはならない。

| 層 | 管理するもの |
|---|---|
| `docs/spec/common.md` (本書) | 全 Skill 共通の Why・要件・不変条件・変更手順 |
| `docs/spec/<skill-name>.md` | その Skill の Why・要件・設計原則・不変条件・境界条件・例外・受入基準 |
| `src/<skill-name>/SKILL.md` ほか | 実行時に必要な指示・判断ロジック・出力フォーマット・実行フロー |

```text
common.md
  ↓ 継承
<skill-name>.md
  ↓ defines
SKILL.md
  ↓ executes
実行時の振る舞い
```

### 1.2 spec を持たない Skill

spec は必須ではない。ただし **spec が無い Skill は「設計判断が `SKILL.md` だけで完結している」という状態**であり、設計上の判断を新たに加えるときは spec を作ってから実装する。

## 2. 共通の不変条件

### CINV-01: 明示起動のみ

すべての Skill は `agents/openai.yaml` で `allow_implicit_invocation: false` を維持する。ユーザーが明示的に起動したときだけ動く。

`SKILL.md` の `description` も明示起動を前提とした書き方にする。**暗黙起動の条件を description に書かない** — 設定と食い違い、利用者の期待を裏切る。

### CINV-02: 配布物の自己完結

`src/<skill-name>/` 配下から、**リポジトリ内部のパスを参照しない。** 配布 ZIP に入るのは `src/<skill-name>/` だけなので、`docs/` `plans/` `tools/` への参照は利用者の手元で解決できない。

根拠や出所を示す必要がある場合は、参照ではなく実体を配布物へ書く。

### CINV-03: ユーザーの価値判断を代行しない

客観的に確認できる事実と、ユーザーにしか決められない価値判断 (目的・優先順位・許容できるリスク・好み) を区別する。**後者を Skill が確定してはならない。**

不可逆な操作や高リスクの判断では、本人の明示的な意思表示を求める。

### CINV-04: 根拠のない一般化をしない

外部の研究・文献・情報源を根拠として挙げるとき、**そこに書かれていないことを、そこの結論として記述しない。** 転用であれば転用と書く。

### CINV-05: 実行していないことを実行済みと書かない

検証・生成・設定反映・外部への操作について、**実際に行っていないことを行ったように書かない。** 「そう書いてあること」と「実行して確かめたこと」を区別する。

- 静的な検査に通ったことを、実行時の振る舞いを検証した証拠として扱わない
- 実行環境の機能を利用できなかった場合、代替物を成果として提示しない (§3.3)
- 未実施の検証は未実施として記録する

これは §3.2 (外部情報を取得できなかった場合) を、外部情報以外の実行結果すべてへ広げたものである。

## 3. 外部情報の取得

Skill が実行時に外部情報を取得できるかは環境に依存する。**取得できる前提で規定を書かない。**

### 3.1 取得可否の宣言

各 Skill の spec は、外部情報取得について次のどれかを明示する。

| 区分 | 意味 |
|---|---|
| 利用する | 実行時に取得を試みる。取得できない場合の振る舞いを spec に書く |
| 利用しない | 取得を試みない。その理由を spec に書く |

### 3.2 取得できなかった場合

**「外部で確認できるはずだから確認しない」という判断をしてはならない。** 実際に確認できたかどうかで分岐する。取得を試みて得られなかった場合は、次のいずれかを行う。

1. その事実が結論を大きく変えるなら、その点だけをユーザーへ確認する
2. そうでなければ合理的な仮定を置き、**最終回答で仮定であることを明示する**

黙って未確認の事実を確定事項として扱わない。

### 3.3 実行環境の機能に依存する場合

Skill が実行時のツール (検索・ファイル読取・画像生成など) に依存する場合、spec は**どの機能へ依存し、利用できないときどう振る舞うか**を書く。

ツールのAPI名・モデル名・引数の形式は実行環境側の仕様なので、spec や実装へ固定しない。利用できなかった機能については、代用したものを本来の成果として説明しない (CINV-05)。

## 4. 変更手順

Skill を変更するときは次の順で行う。

1. 変更要求を分析する
2. 本書および該当 Skill の spec の既存要件との整合性を確認する
3. 必要なら spec を先に変更する
4. 実装 (`SKILL.md` ほか) を変更する
5. spec が受入基準・テストケースを持つ場合は実施する
6. `npm run check` を通す
7. spec と実装に差分が無いことを確認する

**既存 spec と矛盾する実装だけの変更は禁止する。**

---

## 5. 変更完了条件

次をすべて満たした時点で完了とする。

1. spec の該当要件を特定できている
2. 変更内容が spec と矛盾していない
3. 必要なら spec が先に更新されている
4. 実装へ変更が反映されている
5. 受入基準・テストケースがある場合は結果を記録している
6. `allow_implicit_invocation: false` が維持されている (CINV-01)
7. `src/` からリポジトリ内部のパスを参照していない (CINV-02)
8. spec に存在しない設計判断を実装だけへ追加していない
9. `npm run check` が 0 error / 0 warn

---

## 6. spec へ書くべき変更かの判定

新しい挙動を加えるとき、**実装詳細か、振る舞いを規定する設計判断か**を判定する。次に該当するものは spec へ書く。

- 起動条件・適用条件が変わる
- ユーザーへ何を尋ねるか、尋ねないかが変わる
- 出力の形式や構造が変わる
- ユーザー入力の解釈が変わる
- 処理の終了条件が変わる
- 安全性・本人判断の扱いが変わる
- 外部情報の使い方が変わる

文章表現の調整、リファクタリング、例の追加など**外部から見た振る舞いを変えない変更**は、spec 更新を必須としない。

---

## 7. 記述の規約

- Skill 本文・spec ともに日本語で書く
- `SKILL.md` は実行時にコンテキストを消費するため簡潔に保つ (40KB で検証が WARN)。長い背景説明は spec 側へ置く
- spec は `SKILL.md` や Method Card の文章をそのまま重複させない。**同じことを 2 箇所に書かない**

重複の線引きは**高さ**で決める。spec は「何が成り立っていなければならないか」(契約) を書き、実装は「それをどう実行するか」(手順) を書く。

| 例 | spec | 実装 |
|---|---|---|
| 検証方法 | 何を Cover するか、いつ使ってよく、いつ使ってはならないか | 具体的な手順、出力欄、判定ラベル |
| 入力収集 | 何を必須とし、何を入力済みとみなさないか | 提示するテンプレートと文面 |
| 検証ゲート | どのゲートが何を保証するか | 各ゲートの確認文言と記録形式 |

**同じ高さの記述が 2 箇所にあるときだけ重複とみなす。** 契約を spec に、手順を実装に置くのは重複ではない。
